# 03. Обмен данными между телефонами

## Какую задачу решает протокол

В походе у телефонов нет ни сотовой сети, ни интернета. Связь есть только между теми, кто сейчас рядом, и состав этих пар постоянно меняется: колонна растягивается, кто-то отстаёт, на привале все собираются вместе. При этом каждому телефону нужно знать о группе всё важное: кто объявил тревогу, кто ответил на перекличку, где и когда последний раз слышали каждого. Серверу нужны GPS-точки всех участников, а отправить их может только телефон, которому повезло поймать сеть.

Поэтому каждый телефон хранит всё, что знает о группе, и при каждой встрече с соседом сверяет с ним свои данные: сосед досылает то, чего у меня нет, я досылаю то, чего нет у него. Так записи постепенно расходятся по всей группе, в том числе через посредников, и никакой маршрутизации не нужно. В распределённых системах такой способ называют эпидемической рассылкой, а регулярную сверку данных между узлами называют анти-энтропией.

Ниже используются такие слова. Сосед: телефон, с которым сейчас есть соединение Nearby. Запись: любая единица данных, которая хранится и передаётся (событие, состояние участника или точка трека). Автор: участник, на телефоне которого запись создана.

## Что передаётся

| Вид записи | Что это | Кто создаёт | Как сливается | Сколько |
|---|---|---|---|---|
| Событие (`ControlEvent`) | Вступил, маршрут начат, отлучка, перекличка, ответ на перекличку, тревога, SOS, снятие, маршрут завершён | Автор, по действию человека | Множество: запись либо есть, либо нет | Десятки за поход |
| Состояние участника (`MemberState`) | Последняя позиция, заряд, кого участник слышит и как давно | Сам участник, раз в 15 с | Побеждает больший номер состояния, хранится одно на участника | По одному на человека |
| Точка трека (`LocationPoint`) | GPS-точка для сервера | Сам участник, после прореживания | Множество | Около 300 в час на человека |

События и точки после создания не меняются. Слияние двух наборов событий означает их объединение, и порядок, в котором записи пришли, на результат не влияет. Такую структуру в теории называют grow-only set, это простейший вид CRDT (структуры данных, которые сходятся сами при любом порядке слияния).

## Нумерация по авторам

Чтобы сверяться, телефонам нужна короткая сводка «что у меня есть». Список идентификаторов всех записей для этого не годится: только точек трека за день набираются тысячи, и сводка весила бы сотни килобайт.

Поэтому каждый автор нумерует свои записи подряд, отдельно в каждом потоке: события 1, 2, 3 и точки 1, 2, 3 имеют независимые счётчики. Сводка превращается в набор чисел «от автора X у меня есть события до 57-го и точки до 412-й», и её размер зависит только от числа участников. Для группы из 20 человек это около 3 КБ JSON и около 1 КБ после сжатия.

Сводка по номерам верна, только если у каждого телефона по каждому автору хранится непрерывный префикс потока: если есть запись 57, то есть и все записи с 1 по 56. Это свойство держится на трёх правилах.

1. Автор выдаёт номер и сохраняет запись одной транзакцией. Дыр и повторов у автора не бывает.
2. Отправитель шлёт записи одного автора по возрастанию номера, начиная со следующего после того, что, по его сведениям, есть у соседа.
3. Получатель принимает запись, только если её номер ровно на единицу больше его максимума по этому автору. Меньший номер означает повтор, такая запись отбрасывается. Больший означает, что предыдущие записи ещё не пришли; запись тоже отбрасывается и придёт снова в правильном порядке.

Если связь оборвалась посреди передачи, у получателя остаётся префикс покороче, и при следующей встрече сверка начнётся с этого места. Отдельной логики восстановления после разрыва нет.

Тревоги нужно доставлять раньше накопившихся точек. Будь у автора один общий поток, тревога с номером 120, отправленная раньше точек 50-119, создала бы дыру. Два потока решают это: события всех авторов уходят первыми, точки досылаются следом, и порядок внутри каждого потока не нарушается. Состояние участника вообще не нумеруется подряд, там хранится только последнее, поэтому его можно слать в любой момент.

## Сеанс между соседями

Соединение Nearby живёт долго, пока соседи рядом. Для каждого соседа движок синхронизации (`SyncEngine`) хранит `peerKnown`: что, по его сведениям, у соседа уже есть.

### Сообщения

```kotlin
// Сводка: что у меня есть. Отправляется при подключении, каждые 10 с и по просьбе соседа.
// Это же сообщение работает как heartbeat: по нему сосед понимает, что я рядом.
@Serializable
data class Hello(
    val v: Int,                       // версия протокола
    val groupTag: String,             // тег группы; при несовпадении соединение рвётся
    val from: String,                 // мой member_id
    val control: Map<String, Long>,   // автор -> последний номер события в моём префиксе
    val locations: Map<String, Long>, // автор -> последний номер точки
    val states: Map<String, Long>,    // участник -> номер его последнего состояния у меня
)

// Порция записей, которых нет у соседа.
@Serializable
data class Delta(
    val control: List<WireControlEvent> = emptyList(),
    val states: List<WireMemberState> = emptyList(),
    val locations: List<LocationPoint> = emptyList(),
    val more: Boolean = false,        // у меня есть ещё что-то для тебя, пришли свежую сводку
)

// На проводе событие и состояние несут свой текущий возраст (раздел о свежести).
@Serializable data class WireControlEvent(val event: ControlEvent, val ageMs: Long)
@Serializable data class WireMemberState(val state: MemberState, val ageMs: Long)
```

`MeshCodec` превращает сообщение в байты: один байт версии формата, затем JSON, сжатый gzip. JSON выбран ради отладки: любое сообщение можно распечатать в лог и прочитать. Gzip хорошо сжимает повторяющиеся UUID и имена полей. Декодер игнорирует неизвестные поля, а неизвестное значение типа события превращает в `UNKNOWN`; так новое поле или новый тип в будущей версии не ломают обмен со старой. Одно сообщение после сжатия занимает не больше 32 КБ; если `Delta` получилась больше, движок делит её пополам.

### Правила сеанса

| Повод | Действие |
|---|---|
| Сосед подключился | Завести `peerKnown` пустым и отправить ему Hello |
| Пришёл Hello соседа | Заменить `peerKnown` содержимым Hello целиком и ответить одной Delta (состав ниже) |
| Пришла Delta | Применить через `MeshStore.apply`, отметить в `peerKnown`, что присланные записи у соседа есть. Если появились новые события, сразу разослать их остальным соседям. Если в Delta стоит `more`, сразу отправить этому соседу Hello |
| Появилось своё новое событие или своё новое состояние | Сразу отправить его всем соседям, у которых его нет по `peerKnown` |
| Прошло 10 с | Отправить Hello каждому соседу |
| От соседа 45 с не было ни одного сообщения | Разорвать соединение; обнаружение найдёт соседа заново |

#### Первое сообщение соседа: Delta раньше Hello

Первым разобранным сообщением от соседа должен быть Hello своей группы с `from`, равным его `member_id`. Hello с чужим `groupTag` или чужим `from` рвёт соединение — и первым, и в любой момент позже.

Delta, пришедшая раньше первого Hello, соединение **не рвёт**. Движок кладёт её в буфер сеанса (`pendingBeforeHello`, не больше 16 Delta) и не применяет. Когда приходит валидный Hello, движок отвечает на него как обычно, а затем применяет отложенные Delta по порядку. Если до Hello накопилось больше 16 Delta, сосед считается сломанным и соединение рвётся.

Почему не рвать сразу, как было задумано: каждый телефон отправляет Hello при подключении и почти тут же отвечает Delta на Hello соседа. Порядок доставки двух соседних сообщений не гарантирован: в `InMemoryNetwork` у каждого сообщения своя случайная задержка 30–150 мс (плюс 0,2–3 с у доли `reorderRate`), а Hello может и вовсе потеряться (`lossRate`). Со строгим правилом Delta обгоняла Hello, соединение рвалось в первую же секунду, и в симуляции шесть из восьми сценариев `MeshSimulationTest` не сходились: тревога из цепочки A-B-C-D не доходила до D. С буфером все сценарии зелёные. Отложенная Delta ничего не ломает: записи в ней проходят те же правила `MeshStore.apply`, что и любые другие, а применяются только после того, как Hello подтвердил, что сосед из нашей группы. Регрессионный тест — `SyncEngineSessionTest`, «Delta до первого Hello буферизуется и применяется после валидного Hello».

После каждой отправки движок отмечает отправленное в `peerKnown`, чтобы не слать одно и то же дважды. Это оптимистичная оценка: сообщение могло потеряться. Поэтому сводка соседа заменяет `peerKnown` целиком. Если что-то не дошло, следующий Hello покажет это, и недостающее уйдёт снова.

В первой версии протокола было другое правило: брать по каждому автору максимум из Hello и того, что уже отправлено. Симуляция показала, что с ним одна потерянная Delta оставляет дыру до конца соединения: отправитель уверен, что сосед всё получил, а сосед отбрасывает все последующие записи этого автора как идущие не по порядку. В стабильной цепочке из четырёх телефонов с потерей 5% сообщений такой обмен не сошёлся ни в одном из 20 прогонов, в среднем не дошло около 1300 точек. С заменой сошлись все 20 прогонов.

### Ответ на сводку

На каждый Hello соседа телефон отвечает одной Delta:

1. все события, которых нет у соседа, по возрастанию номера внутри автора (не больше 200 за раз);
2. все состояния участников, которые у меня новее, чем у соседа;
3. одну порцию точек: до 300 штук.

Если после этой Delta у меня остаётся что-то для соседа, в ней ставится `more`, сосед сразу присылает свежую сводку и получает следующую порцию. Получается саморегулирующийся цикл: следующая порция уходит только после того, как сосед принял предыдущую и сообщил об этом своей сводкой. Новая тревога никогда не стоит в очереди за мегабайтом трека, и движку не нужно знать, подтвердил ли Nearby доставку конкретного сообщения. Без флага `more` следующая порция ждала бы периодического Hello, и в `MeshSimulationTest` две половины группы после часа порознь сходились бы примерно за 30 с вместо 11 с.

Порядок авторов в порции точек: сначала мои собственные точки, затем остальные авторы по кругу, начиная с места, которое зависит от пары «я и сосед». Если к новичку одновременно подключились несколько соседей, они чаще шлют ему разных авторов, а не одно и то же.

Точки автора X не отправляются соседу, если сосед сейчас сам слышит X (это видно из его состояния, поле `heardAgoMs`, и X слышен меньше 30 секунд назад): такие точки он получит от самого X. Исключение одно: мои собственные точки отправляются всегда. В `MeshSimulationTest` это правило убрало повторы точек в обычной работе полной сетки, где без него лишних точек было около 6 % от нужных, а с ним меньше 0,1 %. При встрече двух половин группы повторы идут через соседей, которые автора напрямую не слышат, и там правило их не сокращает. На скорость сходимости оно не повлияло.

### Что уходит сразу

События (свои и чужие) и своё состояние отправляются соседям немедленно: это тревоги, SOS, ответы на перекличку, и их мало. Чужие состояния и все точки отдаются только в ответ на сводку соседа. В полной сетке немедленная пересылка всего полученного приводила бы к тому, что каждое состояние приходило бы к соседу по три раза. Задержка чужого состояния из-за этого не больше 10 секунд, что при пороге «Не слышно» в 60-120 секунд незаметно.

### Применение Delta

`MeshStore.apply` выполняется одной транзакцией и сам читает текущие максимумы внутри неё. Две Delta от разных соседей, пришедшие одновременно, применяются по очереди.

| Что пришло | Правило |
|---|---|
| Событие автора X с номером n | Принять, если n равен моему максимуму по X плюс один. Если n не больше максимума, это повтор. Если больше чем на единицу, отбросить |
| Точка автора X с номером n | То же правило, поток точек отдельный |
| Состояние участника X | Принять, если его номер больше моего. Своё состояние от других не принимать |
| Запись с тем же автором и номером, но другим UUID | Оставить первую, записать конфликт в лог и в диагностику |
| Событие неизвестного типа, точка с недопустимыми значениями | Сохранить, чтобы не разорвать префикс, но не учитывать в правилах и не отправлять на сервер |

Последнее правило важно. Если бы телефон отбрасывал запись за её содержимое, он никогда не принял бы и следующие записи этого автора, и поток автора застрял бы на всех телефонах навсегда. Поэтому отбрасываются только записи, которые нельзя поставить в префикс (повтор или не тот номер), а сомнительное содержимое хранится с пометкой.

### Цена повторов

Повторная доставка безвредна: правило «ровно следующий номер» отбрасывает повторы, сервер отсеивает их по UUID. Повторы стоят только трафика. В симуляции новичок, который подключился сразу к трём соседям с общей историей за час, получил примерно по 0,5 лишней точки на каждую нужную и догнал историю за 3 секунды. При объёмах похода (десятки килобайт после сжатия) это допустимо.

## Свежесть без общих часов

Часы на телефонах в походе могут расходиться на минуты, их можно перевести вручную. Сравнивать время, записанное разными телефонами, поэтому нельзя. Вместо времени каждая запись несёт свой возраст: сколько миллисекунд прошло с момента её создания.

Каждая запись в хранилище получает отметку свежести.

```kotlin
data class Stamped<T>(
    val value: T,
    val ageAtReceiptMs: Long,      // возраст записи в момент, когда она пришла ко мне
    val receivedAtElapsedMs: Long, // SystemClock.elapsedRealtime() в момент получения
    val receivedBootId: String,    // номер загрузки телефона (Settings.Global.BOOT_COUNT)
    val receivedAtWallMs: Long,    // настенное время получения, запасной вариант
)
```

Текущий возраст записи равен `ageAtReceiptMs + (elapsedNow - receivedAtElapsedMs)`, если телефон с тех пор не перезагружался. Монотонные часы `elapsedRealtime` идут и во сне, но сбрасываются при перезагрузке; это видно по номеру загрузки, и тогда вместо монотонных часов берётся разница настенных, а возраст помечается как примерный. Своя только что созданная запись имеет возраст 0. При отправке в `WireControlEvent` и `WireMemberState` кладётся текущий возраст.

Ошибка возраста складывается из задержек передачи на каждом переходе. В симуляции оценка последнего контакта бывала меньше истинной не больше чем на 0,4 секунды.

Точки трека возраст не несут. Для сервера у них есть `recorded_at` из `Location.time`. Это UTC-время фиксации по часам телефона, и документация Android прямо предупреждает, что оно не монотонно; на расчёты в приложении оно не влияет, а спецификация сервера сама оговаривает, что расхождение часов может менять порядок точек на карте. Возраст фиксации в состоянии участника считается по `Location.elapsedRealtimeNanos`.

## Кого телефон слышит

`PresenceTracker` запоминает момент (по монотонным часам), когда от соседа пришло сообщение, которое удалось разобрать. Сосед «слышен сейчас», если сообщение было не позже 30 секунд назад. Hello идёт каждые 10 секунд, так что сосед перестаёт считаться слышимым после трёх пропущенных сводок. Встроенное событие Nearby о разрыве соединения для этого не используется: документация не говорит, через сколько оно срабатывает.

В своё состояние телефон кладёт `heardAgoMs`: кого из участников он слышал за последние 10 минут и сколько миллисекунд назад. Так сведения о том, что участника X недавно слышал сосед, доходят до телефонов, которые X напрямую не слышат.

Последний контакт группы с участником X телефон оценивает так:

```text
lastContact(X) = min(
  моё прямое наблюдение X,
  возраст последнего состояния X,
  возраст последнего события X,
  для каждого участника O: возраст состояния O + O.heardAgoMs[X]
)
```

Это локальная оценка. Два телефона с одинаковым набором записей могут получить немного разные значения, потому что записи пришли к ним в разное время и каждый слышит своих соседей. Статусы «Не слышно» у разных людей поэтому могут появиться с разницей в несколько секунд. Состояние тревог устроено иначе: оно зависит только от набора событий и одинаково на всех телефонах, получивших одни и те же события.

Насколько оценка отстаёт от правды, зависит от числа переходов. В симуляции линии из пяти телефонов худшая оценка для участника на расстоянии одного перехода была около 10 с, двух около 18 с, трёх около 28 с, четырёх около 33 с. Порог «Не слышно» (120 с, в режиме демо 60 с) с запасом выше этих значений, так что ложное «Не слышно» из-за пересылки через посредников модель не даёт. На телефонах эту цифру ещё предстоит измерить.

## Транспорт поверх Nearby Connections

| Параметр | Значение | Почему |
|---|---|---|
| Стратегия | `P2P_CLUSTER` | Каждый может подключаться к каждому, сетка без центра |
| serviceId | `ru.pereklichka.g.<tag>`, tag это первые 8 байт HMAC-SHA256 с ключом-токеном от строки `pereklichka-mesh`, в hex | Телефоны чужих групп друг друга не находят. Токен в эфир не попадает и не совпадает с хешем, который хранит сервер |
| Имя устройства в Nearby | мой `member_id` | Понятно, кто нашёлся, ещё до соединения |
| ConnectionType | `NON_DISRUPTIVE` в `AdvertisingOptions` и `ConnectionOptions` (у `DiscoveryOptions` такого параметра нет) | Nearby не трогает Wi-Fi и Bluetooth, телефон не теряет интернет для выгрузки |
| Принятие соединения | Автоматически, без сверки кода | Чужих отсекает serviceId. Документация Nearby советует аутентификацию; на MVP этот риск принят |
| Соединения | обычных до 3, четвёртое только для телефона из другой части сети | Реальный предел Bluetooth около 3-4 соединений; резерв нужен для вернувшегося отставшего |

Политика соединений:

1. Advertising (`startAdvertising`) включён всё время, пока работает служба.
2. Discovery (`startDiscovery`) включён, пока соединений меньше трёх. При трёх discovery выключается: он нагружает радио, а подключённым соседям не нужен. Раз в минуту discovery включается на 15 секунд, чтобы заметить телефоны, которых не слышит никто из моей части сети.
3. Нашёлся телефон своей группы. Если мой `member_id` меньше (сравнение строк), я запрашиваю соединение сразу. Если больше, жду 10 секунд: обычно за это время он подключится ко мне сам; если нет, запрашиваю сам. Если двое всё-таки постучались одновременно, Nearby, по словам его разработчика, намеренно отклоняет одно из двух соединений.
4. Четвёртое соединение (и входящее, и исходящее) разрешено только с участником, последний контакт с которым больше 30 секунд или которого группа ещё не знает. Это «телефон из другой части сети»: отставший, который вернулся, или половина группы, шедшая отдельно.
5. После неудачного запроса повтор с паузой 2, 4, 8 секунд и так до 30 секунд.
6. Первое сообщение по новому соединению это Hello. Если в нём чужой `groupTag` или `from` не совпадает с именем устройства в Nearby, соединение рвётся.

Зачем нужен резерв четвёртого слота. Без него телефоны, набрав по три соединения, принимают ещё одно входящее от любого телефона и быстро достигают предела четыре. Если пять телефонов успели связаться каждый с каждым, шестой не может подключиться ни к кому, хотя все рядом. В модели соединений телефон, подошедший позже, оставался без соединения в 15-31% случаев для групп от 6 до 12 человек; с резервом таких случаев не было ни одного на тысячу прогонов. Для четырёх телефонов на демо разницы нет: полная сетка из трёх соединений у каждого получается сама.

Перед стартом транспорт проверяет, что Bluetooth включён и сервисы Google Play доступны. С конца 2026 года Nearby перестаёт сам включать Bluetooth и Wi-Fi, поэтому при выключенном радио экран просит человека включить его.

Для проверки пересылки через посредника на одном столе в диагностике есть список заблокированных участников. Транспорт не подключается к ним и отбрасывает их сообщения, и цепочку «A не слышит C, B слышит обоих» можно показать, не разнося телефоны по разным комнатам. На защите об этом говорится вслух.

## Повреждённые сообщения

Сообщение, которое не удалось разобрать, отбрасывается и учитывается в диагностике; после трёх таких сообщений подряд от одного соседа соединение рвётся. Отрицательный возраст заменяется нулём, возраст больше суток ограничивается сутками. Запись с номером меньше единицы отбрасывается, потому что в префикс её всё равно не поставить. Запись без автора или без номера делает неразборчивым всё сообщение: в моделях эти поля обязательны.

## Тайминги

Значения лежат в `SyncConfig`, `Thresholds`, `PresenceTracker`, `ConnectionPolicy`, `TrackThinner` и `GroupViewProvider`. Из диагностики меняется только режим демо, он переключает порог «Не слышно».

| Что | Значение |
|---|---|
| Hello каждому соседу | каждые 10 с и сразу после Delta с `more` |
| Сосед не слышен | 30 с без сообщений |
| Разорвать молчащее соединение | 45 с без сообщений |
| Своё состояние | каждые 15 с |
| «Не слышно» | 120 с без контакта, в режиме демо 60 с |
| Окно переклички | 3 мин |
| Запрос GPS | каждые 5 с, высокая точность |
| Точка в трек | смещение 15 м или прошла минута |
| Сообщение | не больше 32 КБ после сжатия |
| Ответ на сводку | до 200 событий, все новые состояния, до 300 точек |
| Пересчёт статусов | раз в 2 с и при изменении данных |

## Как это проверено

Правила протокола прогнаны в исполняемой модели: цепочки, полная сетка, встреча двух половин группы после часа порознь, новичок с тремя соседями, случайные разрывы и восстановления связей, потеря, дублирование и перестановка 5% сообщений, перезагрузка телефона. Во всех прогонах непрерывный префикс не нарушился ни разу, повторов в хранилище не было, данные сошлись. Тревога в цепочке из четырёх телефонов доходила до последнего быстрее чем за 0,4 с модельного времени. Правила тревог проверены property-тестами модели, на телефоне их повторяет `GroupCalculatorTest`. Модель проверяет логику протокола и не заменяет испытаний на телефонах: задержки, пропускная способность и поведение Nearby в ней заданы оценочно.

## Чего в протоколе сознательно нет

Нет подтверждений на каждое сообщение: их заменяет сверка сводок, и всё недошедшее досылается само. Нет маршрутизации и таблиц соседей, потому что в группе до 20 человек каждый передаёт всё всем. Нет логических часов: свежесть считается по возрасту, а порядок для тревог задают ссылки `refs`. Нет подписей событий: на MVP группу отделяет serviceId, подписи Ed25519 из ресерча остаются расширением.
